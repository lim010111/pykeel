# 도메인 문서

스킬이 코드를 살펴볼 때 이 저장소의 도메인 문서를 읽는 방법이다. 단일 컨텍스트 저장소다.

## 살펴보기 전에 읽을 것

- `GLOSSARY.md`: 용어 정의
- `docs/adr/`: 되돌리기 비싼 기술 결정. 작업할 영역에 닿는 ADR을 읽는다.
- `docs/plan.md`: 목적, 원칙, 로드맵 단계별 범위와 완료 기준, 미룬 결정, 열린 질문
- `docs/design/<모듈>.md`: 핵심 모듈의 설계 메모. 그 모듈을 다룰 때 읽는다.
- `docs/research/`: 1차 출처로 확인한 사실. plan.md와 ADR이 링크로 가리킨다.

파일이 없으면 조용히 넘어간다. `GLOSSARY.md`와 ADR은 `/domain-modeling`이 용어나 결정이 실제로 정해질 때 만든다.

## 결정을 남기는 곳

- 로드맵 단계의 범위, 원칙, 미룬 결정: `docs/plan.md`
- 되돌리기 비싼 기술 결정: `docs/adr/`
- 핵심 모듈 내부 설계: `docs/design/<모듈>.md`

## 용어

도메인 개념에 이름을 붙일 때(이슈 제목, 리팩터링 제안, 가설, 테스트 이름) `GLOSSARY.md`에 정의된 용어를 쓰고, _Avoid_에 적힌 말 대신 그 용어를 쓴다.

필요한 개념이 GLOSSARY에 없으면 둘 중 하나다. 프로젝트가 쓰지 않는 말을 만들고 있거나(다시 생각한다), 실제 빈칸이다(`/domain-modeling`에 넘길 것으로 적어 둔다).

## 결정과 어긋날 때

결과물이 ADR이나 plan.md의 결정과 어긋나면 드러내서 말한다.

> _ADR-0004(하네스가 Responses 상태를 관리)와 어긋나지만, … 때문에 다시 열 만하다._
