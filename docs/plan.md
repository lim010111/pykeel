# pykeel 계획

이 문서는 2026-11-17 grilling에서 정한 목적, 원칙, 로드맵, 연구 주제, 작업 방식을 정리한 것입니다. 2026-11-18~19에 v0을 앞두고 한 grilling 결과도 반영했습니다. 관련 문서는 다음과 같습니다.

- 용어 정의: [GLOSSARY.md](../GLOSSARY.md)
- 되돌리기 비싼 기술 결정: [adr/](adr/)
- 핵심 모듈 규칙: [AGENTS.md](../AGENTS.md)
- 1차 출처로 확인한 조사 기록: [research/](research/)

## 목적

pykeel은 LLM 호출, 에이전트 루프, Session 관리를 SDK나 에이전트 프레임워크 없이 직접 구현하는 coding agent 하네스입니다. 이 하네스로 하네스 인터페이스가 특정 모델에 얼마나 맞춰져 있는지 측정합니다. 자세한 질문은 아래 연구 주제 절에 있습니다.

- 핵심 모듈은 직접 씁니다. AI 협업자는 핵심 모듈에 대해 설명과 리뷰를 하는 것을 기본으로 합니다. 사용자와 AI 협업자의 공동 목표는 하네스의 완성도입니다.
- 기존 프로젝트와 별개인 독립 저장소로 진행합니다.

## 로드맵

### 공통 구간

| 단계 | 내용 |
|---|---|
| v0 | 동기·비스트리밍 Responses 루프, bash tool, trace를 만듭니다. 무인 실행 장치(bash 시간 제한, 프로세스 트리 정리, 메모리 상한, bwrap 샌드박스)도 여기서 넣습니다. 자세한 내용은 아래 v0 절에 있습니다 |
| E1 | tool 선택 과제 세트의 뼈대와 채점기를 만듭니다 |
| C0 | 비스트리밍 Chat Completions 어댑터를 만들어 EXAONE을 붙입니다. 내부 메시지 모델을 처음으로 고치는 단계입니다 |
| E0 | 평가 실행기를 만들고 파일럿을 돌립니다 |

E1, C0, E0의 순서는 바꿔도 됩니다. 단, C0 전에는 EXAONE을 측정할 수 없습니다. B 전의 수치는 모두 파일럿입니다.

처음 계획은 Chat Completions를 먼저 만드는 것이었습니다. 그런데 2026-11 기준 최신 GPT는 Chat Completions에서 추론과 tool을 함께 쓸 수 없습니다([조사](research/2026-11-18-openai.md)). Chat Completions로 tool을 쓸 수 있는 현행 GPT는 추론을 끈 `gpt-6-luna`뿐이고, Artificial Analysis 기준 Intelligence Index 9, Terminal-Bench 4.0 1.5%로 너무 약합니다([조사](research/2026-11-18-artificial-analysis.md)). 이런 모델로 개발하면 v0이 실패했을 때 하네스 탓인지 모델 탓인지 가르기 어렵습니다. 그래서 실험에서 쓸 GPT 경로인 Responses를 먼저 만듭니다.

### v0

**실행 형태:** 한 번 실행하고 끝나는 CLI 하나입니다(`pykeel run <작업 디렉터리> "<지시문>"` 모양). v0에는 무인 실행만 있으므로 샌드박스를 끄는 옵션도 없습니다.

**정해 둔 것:**

- tool은 function tool `bash` 하나입니다. 파일을 읽고 고치는 일도 셸 명령으로 합니다. 루프를 끝까지 돌리기 위한 최소 세트이고, 실험의 출발 인터페이스는 InterfaceSpec을 분리할 때 따로 정합니다(미룬 결정).
- 모듈 사이클 1단계(실제 데이터 보기)에서 EXAONE에도 tools를 붙인 요청을 curl로 보내 원본을 저장합니다. tool_calls가 실제로 오는지, `reasoning_content`를 어떻게 돌려줘야 하는지 확인합니다. tool_calls가 오지 않으면 EXAONE 전제를 E0까지 기다리지 않고 바로 다시 엽니다.
- 같은 단계에서 Responses 응답에 백엔드 식별 필드가 있는지 확인합니다. 조사에서 확인한 `system_fingerprint`는 Chat Completions 응답 필드입니다([조사](research/2026-11-18-openai.md)). 확인 결과 Responses 응답에는 없었습니다([llm 설계 메모](design/llm.md)).

**완료 기준:**

1. 작은 확인용 저장소 2~3개(실패하는 테스트가 하나 있는 정도)를 샌드박스 안에서 끝까지 풉니다. 확인용 저장소는 `/usr` 안의 도구(시스템 python3, 표준 라이브러리)만으로 테스트가 돌게 만듭니다.
2. 그 실행의 trace만으로, API를 호출하지 않고 같은 tool 호출 순서를 재현하는 replay 테스트가 통과합니다.
3. 비정상 경로를 일부러 일으켜 확인합니다.
   - 명령 시간 초과: 명령 트리가 정리되고, 그 tool 기록에 시간 초과가 남습니다. 실행은 계속됩니다.
   - 비용 상한: 실행이 멈추고, 마지막 줄에 종료 이유가 남습니다.
   - 하네스 강제 종료: 그 직전까지의 trace가 남고, 샌드박스 안 프로세스는 남지 않습니다. 마지막 줄이 없다는 것이 비정상 종료의 표시입니다.

확인용 저장소는 나중에 과제 세트에 넣지 않습니다. 넣더라도 개발 과제로만 넣습니다. v0을 만들며 실패를 여러 번 들여다본 문제이기 때문입니다.

**첫 실행 전에 할 일:** pykeel 전용 OpenAI 프로젝트를 만들어 그 프로젝트의 키만 쓰고, 그 프로젝트에 월 hard spend limit을 겁니다.

**설계 메모에서 다룰 것:** grilling에서 나왔지만 핵심 모듈의 설계에 속해서 넘겨 둔 것들입니다.

- replay 테스트가 정확히 무엇을 비교하는지(loop, trace)
- flush와 운영체제 버퍼(trace)
- 토큰 상한이 세는 범위. 매 호출마다 다시 보내는 입력 누적을 포함하는지, 캐시 토큰을 어떻게 셀지(loop)
- GPT-6.2를 Responses로 쓸 때의 주의점(llm)
  - top-level `instructions`는 캐시에 맞아도 캐시되지 않은 단가로 과금됩니다. 시스템 프롬프트를 어디에 둘지가 비용에 영향을 줍니다.
  - 대화 앞부분을 고치면 reasoning item이 버려집니다. 버려졌는지는 응답의 `input_transformations`로 알 수 있습니다.
  - `temperature`와 `top_p`를 받지 않습니다. 그래서 기록할 샘플링 설정은 사실상 reasoning effort 정도입니다.
- 이전 item, 특히 reasoning item을 받은 그대로 돌려주는 방법(llm, 내부 메시지 모델)
- OOM으로 죽은 경우를 trace에서 구분할지와 그 방법. 종료 코드로는 판별할 수 없습니다(tools)
- bash 결과를 모델에게 보여 주는 형식. 종료 코드 표시, 긴 출력을 자르는 방식 등이며, 하네스 인터페이스에 속합니다(tools)
- bash 호출 사이에 작업 디렉터리와 환경 변수가 이어지는지, 그 사실을 모델에게 어떻게 알릴지(tools)

### 두 트랙

공통 구간이 끝나면 두 트랙으로 나뉩니다. 두 트랙은 서로를 기다리지 않습니다.

| 하네스 트랙 | 실험 트랙 |
|---|---|
| v1: SSE 스트리밍, tool_call 델타 조립 | L: 선행 연구 조사 |
| v2: asyncio, Ctrl+C 취소 전파 | P: 2×2 파일럿 |
| 그 뒤는 써 보면서 결정합니다 | B: 공식 기준선 |
| | S: 자기개선 루프 |
| | M: 2×2 본 측정(held-out) |

- **L과 P는 관문입니다.** 선행 연구가 이미 같은 질문에 답했거나, 파일럿에서 인터페이스를 바꿔도 성공률이 거의 움직이지 않으면 S에 들어가기 전에 연구 질문을 다시 다듬습니다.
- **L은 코드가 아니라 읽기입니다.** 그래서 v0 단계부터 같이 진행해도 됩니다.
- **실험 트랙은 v1, v2를 기다리지 않습니다.** 동기·비스트리밍 하네스만으로 충분합니다.
- **v2에서 확인할 것:** bwrap의 `--die-with-parent`는 bwrap을 띄운 프로세스가 아니라 **스레드**가 끝날 때 샌드박스를 죽입니다. asyncio로 옮길 때 bwrap을 어느 스레드에서 띄우는지 확인합니다([조사](research/2026-11-18-sandbox.md)).

## 원칙

### 무인 실행

- 샌드박스가 없으면 무인 실행을 시작하지 않습니다. 샌드박스를 끄는 옵션은 대화형 실행에만 둡니다.
- 안전 규칙(샌드박스, 비용 상한, 환경 변수 허용 목록)은 핵심 모듈이 지킵니다. CLI나 설정 같은 주변부로는 이 규칙을 끄거나 우회할 수 없습니다.

**샌드박스**

- 샌드박스에는 필요한 것만 넣습니다(허용 목록). `/usr`(읽기 전용)와 그에 딸린 symlink, `/proc`, `/dev`, 크기를 제한한 `/tmp`, 작업 사본만 넣고, 홈, `/mnt`, `/run`은 넣지 않습니다.
  - 루트 전체를 읽기 전용으로 넣는 방식은 쓰지 않습니다. 개발 환경(WSL2)에서 그 방식으로 실험했더니 샌드박스 안에서 Windows 프로세스 실행(WSL interop), D-Bus를 통한 systemd 접근, 홈 디렉터리와 `/mnt/c` 읽기가 모두 가능했습니다([조사](research/2026-11-18-sandbox.md)). 허용 목록 방식에서는 셋 다 막혔으므로, WSL interop을 시스템 설정(`wsl.conf`)으로 끄지는 않습니다.
- 샌드박스 안의 네트워크는 끕니다. v0에는 켜는 옵션이 없습니다.
- 작업 디렉터리는 항상 사본입니다. 원본 저장소는 건드리지 않습니다.
- 샌드박스 안 명령에는 환경 변수를 모두 비운 뒤 허용 목록(PATH, HOME, LANG 등)만 넘깁니다. 그렇지 않으면 모델이 `env` 한 번으로 API 키를 보고, 그 출력이 다음 요청에 실려 trace와 모델 제공사로 넘어갑니다.
- 샌드박스가 실제로 막고 있는지 확인하는 테스트를 `tests/policy/`에 둡니다. `cmd.exe` 실행, D-Bus 소켓 접근, 홈 디렉터리의 `.ssh` 읽기가 모두 실패하는지 봅니다(`cmd.exe` 검사는 WSL이 아니면 건너뜁니다). 경로는 호스트 기준 절대 경로로 지정합니다. 샌드박스 안의 `~`는 안쪽 `HOME` 값으로 풀리므로, `~/.ssh`로 검사하면 홈이 보이는 상태에서도 통과할 수 있습니다. 이 테스트에는 근거 문서로 [조사 보고서](research/2026-11-18-sandbox.md)를 링크합니다.
- 시간 초과와 메모리에 대한 요구사항은 다음과 같습니다. 구체적인 방법은 tools 모듈을 구현할 때 정합니다.
  - 시간 초과가 나면 명령과 그 자식 프로세스가 모두 정리됩니다.
  - 하네스가 강제로 죽어도 샌드박스 안 프로세스가 남지 않습니다.
  - 메모리 상한은 프로세스 트리 전체에 걸리고, swap으로 빠져나가지 않습니다.

**비밀값**

- API 키는 환경 변수로만 읽습니다. `.env`는 `uv run --env-file .env`로 넣습니다.
- API 키는 trace, 테스트 픽스처, 설계 메모, 로그 어디에도 남기지 않습니다. 저장한 응답과 curl 출력은 픽스처나 설계 메모로 git에 들어가므로 특히 주의합니다.
- 커밋될 수 있는 파일 전체(`git ls-files --cached --others --exclude-standard`)에서 키 모양 문자열과, 설정되어 있다면 실제 키 값을 찾는 검사를 둡니다. 이 검사는 pytest와 pre-commit hook 양쪽에서 돌립니다. hook은 저장소의 `.githooks/`에 두고 `git config core.hooksPath .githooks`로 연결합니다.

**비용**

- 실행마다 모델 호출 횟수 상한과 누적 토큰 상한을 둡니다. 두 값이 설정에 없거나 0이면 실행하지 않습니다. 핵심 모듈에 숨은 기본값을 두지 않습니다. 상한에 걸리면 실행을 멈추고 종료 이유를 trace에 남깁니다.
  - 달러 상한을 두지 않는 이유: v0 상한의 목적은 우발적인 무한 루프를 막는 것입니다. 달러로는 "싼 모델이 수천 번 도는 것"과 "비싼 모델이 한 번 도는 것"을 구분할 수 없습니다. 달러 환산은 분석할 때 trace의 usage로 합니다.
- 바깥 안전장치로 pykeel 전용 OpenAI 프로젝트에 hard spend limit을 겁니다. 한도에 닿으면 429로 막히지만 즉시 막히지는 않습니다.
- 동시 실행 수에는 상한을 두지 않습니다. 직접 지켜봅니다.

### 기록

- 첫 실행부터 요청과 응답의 원본을 남깁니다. 기존 내용은 고치지 않고 덧붙이기만 하는 JSONL 파일로 저장합니다. 남기지 않은 원본은 돈을 다시 내야만 얻을 수 있기 때문입니다.
- trace는 핵심 모듈입니다. 필드 이름과 파일 배치는 설계 메모에서 정하고, 다음은 첫 실행부터 지킵니다.
  - 응답 본문은 파싱하기 전, 받은 텍스트 그대로 기록합니다. 파싱한 뒤 다시 직렬화하지 않습니다. 그래야 파싱에 실패한 응답과 지금은 쓰지 않는 필드도 남습니다.
  - 실패한 시도(HTTP 오류, 타임아웃, 재시도 하나하나)도 기록합니다.
  - 요청 헤더는 기록하지 않습니다(API 키가 들어 있습니다). 응답 헤더는 허용 목록(요청 ID, 처리 시간, 속도 제한)만 남기고, 계정 식별 헤더는 뺍니다.
  - 일이 하나 생길 때마다 바로 덧붙이고 flush합니다. 하네스 프로세스가 죽어도 그때까지의 기록은 남아야 합니다.
  - 실행이 끝난 이유(정상 종료, 턴 상한, 비용 상한, 오류, 중단)를 마지막에 남깁니다. 이 이유는 하네스가 판단합니다. 응답 하나가 끝난 이유(`finish_reason` 등)는 응답 원문에 이미 들어 있습니다.
  - tool 실행마다 종료 코드, 소요 시간, 시간 초과 여부, 잘리기 전 출력 길이를 남깁니다.
- 원본과 함께 다음 정보를 남깁니다.
  - 응답에 실제로 찍힌 모델 ID
  - 샘플링 설정
  - 실행 상한 값(모델 호출 횟수, 토큰)
  - 하네스 커밋과 커밋되지 않은 변경(dirty)이 있었는지 여부
  - 스키마 버전
- Responses의 대화 상태를 서버에 맡기지 않으므로, 요청 원본 하나에 그 시점의 대화 전체가 들어 있습니다([ADR-0004](adr/0004-harness-owns-responses-state.md)).
- 요청 원본이 남아 있으면 그때의 하네스 인터페이스를 trace에서 복원할 수 있습니다. 그래서 InterfaceSpec 분리는 P 직전으로 미룹니다.
- 다음 항목은 나중에 원본으로부터 만듭니다.
  - 대화 내용 없이 지표만 저장하는 모드
  - OTel GenAI 규약에 맞춘 필드 이름
  - 분석용 스키마

  OTel GenAI 규약은 아직 실험 단계입니다. 따르게 되면 어느 버전의 규약인지도 함께 기록합니다.

### 측정

- held-out 과제는 M에서 처음 엽니다. 인터페이스를 고치거나 루프를 돌리는 실행에는 넣지 않습니다.
- held-out 목록은 첫 파일럿 전에 확정해서 따로 떼어 둡니다. 구체적인 분리 방식은 열린 질문입니다.
- 파일럿에 쓴 과제는 held-out에 넣지 않습니다.
- 한 비교 안의 실행은 모두 같은 하네스 커밋(태그)과 같은 모델 스냅샷으로 돌립니다. 실험은 태그에서 돌리고, 하네스 개발은 main에서 계속합니다. 둘 중 하나라도 바뀌면 기준선부터 다시 측정합니다.
- 날짜로 고정된 스냅샷이 없는 모델이 늘고 있습니다(GPT-5.6 이후, EXAONE). 이런 모델은 실행할 때마다 응답의 실제 모델 ID를 기록하고, ID가 바뀌면 기준선부터 다시 측정합니다. 다만 ID가 같아도 가중치가 바뀔 수 있습니다. 그래서 응답 본문의 백엔드 식별 필드(예: Chat Completions의 `system_fingerprint`, EXAONE의 `metadata.weight_version`)도 원본째 남깁니다. Responses 응답에는 같은 역할의 필드가 없고, `model`도 요청한 별칭 그대로 돌아옵니다(2026-11-19, `gpt-6.2-sol`, [llm 설계 메모](design/llm.md)). 그래서 Responses 모델은 가중치가 바뀌어도 응답만으로는 알 수 없습니다. 이 필드를 재측정 기준에 넣을지는 B 직전에 정합니다.

## 연구 주제

> 하네스 인터페이스는 특정 모델에 맞춰져 있다. 모델을 바꾸면 성공률이 얼마나 떨어지고, 자기개선 루프로 그 차이를 얼마나 메울 수 있는가?

- **실험 축:** 지금은 GPT와 EXAONE입니다. 연구 질문 때문에 고른 것이 아니라 당장 쓸 수 있어서 고른 것입니다(OpenAI API 크레딧, EXAONE 무료 구간). 이상적으로는 GPT, Claude, Gemini, Grok처럼 많이 쓰는 모델을 다뤄야 하므로, 나중에 그 모델들로 넓혀 측정합니다.
- **바꾸는 것:** 하네스 인터페이스만 바꿉니다. 루프 코드는 고정합니다.
- **2×2 교차 측정:** 비교하는 두 모델 각각에 맞춘 인터페이스를 모두 같은 자기개선 루프로 만들고, 네 조합을 모두 held-out 과제로 측정합니다. 한쪽만 사람이 손으로 다듬으면 모델 차이와 방법 차이가 섞입니다. 결과 해석은 [GLOSSARY.md](../GLOSSARY.md)의 "2×2 교차 측정" 항목에 있습니다.
- **성능 하락의 두 성분:** 하락에는 모델 능력 차이와 인터페이스 부적합이 섞여 있습니다. "예상 성능"이라는 기준이 없으므로 처음부터 둘을 나눌 수는 없습니다. 루프를 돌린 뒤 회복된 만큼을 인터페이스 부적합분으로 사후에 측정합니다.
- **보고서 서술:** "성능이 떨어져서 루프를 만들었다"는 개발 동기로는 자연스럽습니다. 하지만 보고서에는 "루프를 두 모델에 똑같이 적용하고 교차 측정했다"로 써야 주장이 섭니다.
- **기반 단계:** Session과 컨텍스트 관리 실험(캐시, compaction)이 이 주제의 기반이 됩니다.

### 성공 기준

목표는 깊이 있는 발견 2~3개입니다. 발견 하나마다 다음이 붙어야 합니다.

- 반복 실행에서 나온 신뢰구간
- held-out 과제로 확인한 결과
- 실패를 원인별로 분류한 표
- 재현 스크립트
- 짧은 보고서 한 편

실패한 결과도 발견입니다. 예를 들어 "자동 개선으로는 차이를 X%밖에 못 메웠고, 원인은 Y였다"도 그대로 발견이 됩니다.

### 위험

- **통계적 검정력:** 과제 20개를 5번씩 돌려서는 아주 큰 차이만 구분됩니다. 과제 수를 늘리거나 효과가 큰 질문을 고릅니다. 차이가 드러나지 않으면 "차이 없음"이 아니라 "이 규모로는 판별 불가"라고 정직하게 씁니다.
- **비용:** 실험을 설계할 때 "과제 수 × 반복 수 × 평균 토큰"으로 예산을 먼저 계산합니다.
- **과적합:** 자기개선 루프가 평가 과제에 맞춰 인터페이스를 고치면 성공률이 부풀려집니다. 그래서 개발 과제와 held-out 과제를 분리합니다.
- **EXAONE 무료 구간의 한계:** 지금 무료로 쓸 수 있는 EXAONE은 LG AI연구원 EXAONE API Platform의 K-EXAONE 2.5 하나입니다([조사](research/2026-11-18-exaone.md)).
  - 기본 한도는 하루 100회이고, API key는 30일마다 만료됩니다.
  - 약관상 비상업 이용만 허용됩니다. 입력과 출력은 기본적으로 모델 학습에 쓰이고(거부 가능), 반복적인 동일 요청을 비정상 트래픽으로 막을 수 있다는 조항이 있습니다.
  - 과제 20개를 5번씩, 과제당 15턴 정도로 돌리면 2×2 한 칸에만 1,500회 정도가 필요합니다.

  실험에 쓸 모델을 정할 때(미룬 결정) 이 사실에서 출발합니다.
- **바닥 효과:** Artificial Analysis 기준 K-EXAONE 2.0은 Intelligence Index 8, Terminal-Bench 4.0 0%입니다. 2.5는 아직 실려 있지 않습니다([조사](research/2026-11-18-artificial-analysis.md)). EXAONE의 E2E 성공률이 0%에 붙으면 인터페이스를 바꿔도 움직일 여지가 없어 2×2에서 아무것도 측정되지 않습니다. P 관문에서 확인하고, 그 전에 v0 1단계의 curl 확인에서 처음 엿봅니다.

## 작업 방식

먼저 만들고, 나중에 기존 구현과 비교합니다. 내 설계를 먼저 확정한 뒤에 참고 구현을 읽으므로, 비교는 하되 영향은 받지 않습니다. "나는 X로 했는데 저쪽은 Y로 했다, 이유는 Z다"가 그대로 설계 기록이 됩니다. 여기에 세 가지를 보완합니다.

### 보완 1: 구현과 연구 주제는 순서가 다릅니다

| 대상 | 순서 | 이유 |
|---|---|---|
| 하네스 구현(루프, SSE, Session, 취소, MCP) | 먼저 만들고 나중에 읽습니다 | 남의 설계에 끌려가지 않고 내 설계를 먼저 세우기 위해서입니다 |
| 연구 주제(인터페이스 자동 개선) | 선행 연구를 먼저 읽습니다 | 누가 이미 했는지 모르면 새롭다고 주장할 수 없기 때문입니다 |

선행 연구 후보는 다음과 같습니다.

- 프롬프트 최적화: DSPy, GEPA 계열
- 실패에서 배우는 에이전트: Reflexion, ExpeL
- tool 문서와 설명을 자동으로 다듬는 연구

이 연구들을 훑어서 "기존 연구가 안 한 것"을 확정합니다. 모델 간 교차 적용(2×2)이 그 후보입니다. 남의 하네스 코드가 아니라 방법론을 읽는 것이므로, 먼저 만들고 나중에 읽는다는 원칙과 부딪히지 않습니다.

### 보완 2: 모듈마다 같은 사이클을 돕니다

1. **실제 데이터를 먼저 봅니다.** 예를 들어 파서를 짜기 전에 `curl`로 실제 SSE 스트림과 tool_call 델타를 받아 저장하고 직접 읽어 봅니다. 저장한 데이터는 그대로 테스트 픽스처가 됩니다.
2. **설계 메모를 씁니다.** 어떻게 만들지와 어디서 막힐 것 같은지를 예측까지 적습니다.
3. **구현합니다.**
4. **예측과 실제를 비교합니다.** 예상하지 못한 문제가 가장 값진 기록입니다.
5. **참고 구현을 1~2개 읽고** 설계 메모에 비교 내용을 덧붙입니다.

설계 메모는 `docs/design/<모듈>.md`에 둡니다.
- 모듈마다 파일 하나를 두고, 사이클을 돌 때마다 날짜를 붙인 절을 쌓습니다. 절은 실제 데이터 / 설계와 예측 / 예측과 실제 / 참고 구현 비교로 나눕니다.
- 실제 데이터 원본은 비밀값을 지운 뒤 `tests/fixtures/`에 두고, 메모에서 링크합니다.
- 참고 구현을 보고 만든 부분에는 그 옆에 `> 참고 후 구현: 무엇을, 어디서` 한 줄을 붙입니다.
- 설계 메모의 대상은 핵심 모듈입니다. 주변부에는 이 사이클을 돌지 않습니다.

테스트도 같은 경계를 따릅니다. 테스트는 사실상 명세이기 때문입니다. 핵심 모듈의 동작 테스트(`tests/<모듈>/`)는 핵심 모듈과 같이 다룹니다. 합의한 규칙이 지켜지는지 확인하는 정책 검사 테스트(`tests/policy/`)는 주변부입니다. 자세한 규칙은 [AGENTS.md](../AGENTS.md)에 있습니다.

모듈별로 읽을 참고 구현을 미리 정해 둡니다. 그래야 읽을거리가 끝없이 늘지 않습니다.

| 모듈 | 참고 구현 |
|---|---|
| SSE와 스트림 조립 | openai-python SDK |
| 에이전트 루프 | mini-swe-agent |
| 편집 형식 | Aider |
| MCP | 공식 Python SDK |
| 전체 구조 비교 | pi나 Codex 중 하나 |

### 보완 3: 막혔을 때는 단계를 밟습니다

1. **혼자:** 스펙 문서와 언어 문서만 보면서, 정해 둔 시간(예: 작업 세션 2번)까지 붙잡습니다.
2. **AI 협업자에게 묻기:** 개념이나 프로토콜에 관한 사실을 묻습니다. 예를 들어 "asyncio에서 CancelledError는 어떻게 전파되나?" 같은 질문입니다. 내가 쓴 코드에 대한 리뷰와 엣지 케이스 제안도 받습니다. 코드를 생성해 달라는 요청과 "기존 하네스는 어떻게 하나"는 묻지 않습니다.
3. **참고 구현:** 그래도 막히면 해당 부분만 읽습니다. 이 경우 "참고 후 구현"이라고 기록에 표시합니다.

직접 만들면서 부딪혀 보고 정할 것들입니다. 각 결정을 다시 꺼낼 시점을 함께 적었습니다.

| 미룬 결정 | 다시 꺼낼 시점 |
|---|---|
| 실험의 출발 인터페이스(tool 세트, 편집 형식). v0은 bash 하나로 시작합니다. GPT가 학습한 `apply_patch`와 `shell`(Responses 전용 내장 tool)도 이때 후보로 놓고 봅니다 | InterfaceSpec을 분리할 때(P 직전) |
| bwrap 세부 설정, 메모리 제한과 kill 방식. 요구사항은 원칙 절에 있습니다 | v0에서 무인 실행 장치를 구현할 때 |
| tool 선택 과제 세트 설계, E2E 과제의 형식·출처·개수, 과제 환경에 `/usr` 밖 도구를 넣는 방식 | E1, E0 |
| 실험에 쓸 모델(위험 절의 EXAONE 무료 구간 한계 참고), 실험별 예산, EXAONE 속도 제한 | E0 파일럿 직전 |
| 날짜 스냅샷이 없는 모델의 재측정 기준(백엔드 식별 필드를 넣을지) | B 직전 |
| 많이 쓰는 모델(Claude, Gemini, Grok 등)로 넓히기, 그때의 교차 측정 설계(모델 쌍마다 2×2 또는 N×N) | M 이후 |
| 내부 메시지 모델 ADR | C0 이후 |
| InterfaceSpec 분리 | P 직전 |
| 지표 전용 모드, OTel 필드 이름, 분석 스키마 | 첫 분석을 할 때 |
| 대화형 권한 확인, REPL 범위, MCP·스킬·서브에이전트 | v2 이후. MCP 사양은 2026-07-28판에서 handshake와 session이 빠졌으므로 그때 다시 확인합니다 |
| 컨텍스트 관리, compaction | 긴 과제에서 컨텍스트가 넘칠 때 |
| LangGraph 비교 실험 | B 이후. 같은 과제 세트로 성공률, 토큰, 턴 수, 코드량, 감춰진 것과 통제할 수 없었던 것을 비교합니다 |
| 선행 연구 1차 지도(서브에이전트로 뽑을지) | L을 시작할 때 |
| Python 3.15 전환 | 의존성들이 3.15 지원을 표시할 때 |
