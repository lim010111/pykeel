# pykeel 계획

이 문서는 2026-11-17 grilling에서 정한 목적, 원칙, 로드맵, 연구 주제, 작업 방식을 정리한 것입니다. 관련 문서는 다음과 같습니다.

- 용어 정의: [GLOSSARY.md](../GLOSSARY.md)
- 되돌리기 비싼 기술 결정: [adr/](adr/)
- 핵심 모듈 규칙: [AGENTS.md](../AGENTS.md)

## 목적

pykeel은 LLM 호출, 에이전트 루프, Session 관리를 SDK나 에이전트 프레임워크 없이 직접 구현하는 coding agent 하네스입니다. 이 하네스로 하네스 인터페이스가 특정 모델에 얼마나 맞춰져 있는지 측정합니다. 자세한 질문은 아래 연구 주제 절에 있습니다.

- 핵심 모듈은 직접 씁니다. 에이전트는 핵심 모듈에 대해 설명과 리뷰만 합니다.
- 기존 프로젝트와 별개인 독립 저장소로 진행합니다.

| 모델 | OpenAI API 크레딧, EXAONE 무료 구간 | 실험에 쓸 모델은 미룬 결정입니다 |

## 로드맵

### 공통 구간

| 단계 | 내용 |
|---|---|
| v0 | 동기·비스트리밍 Chat Completions 루프, tool, trace를 만듭니다. 무인 실행 장치(bash 시간 제한, 프로세스 그룹 kill, bwrap 샌드박스)도 여기서 넣습니다 |
| E1 | tool 선택 과제 세트의 뼈대와 채점기를 만듭니다 |
| R0 | 비스트리밍 Responses 어댑터를 만듭니다. 내부 메시지 모델을 처음으로 고치는 단계입니다 |
| E0 | 평가 실행기를 만들고 파일럿을 돌립니다 |

E1, R0, E0의 순서는 바꿔도 됩니다. 단, R0 전에 측정한 GPT 수치는 모두 파일럿으로만 봅니다.

### 두 트랙

공통 구간이 끝나면 두 트랙으로 나뉩니다. 두 트랙은 서로를 기다리지 않습니다.

| 하네스 트랙 | 실험 트랙 |
|---|---|
| v1: SSE 스트리밍, tool_call 델타 조립 | L: 선행 연구 조사 |
| v2: asyncio, Ctrl+C 취소 전파 | P: 2×2 파일럿 |
| 그 뒤는 써 보면서 결정합니다 | B: 공식 기준선 |
| | S: 자기개선 루프 |
| | M: 2×2 본 측정(held-out) |

- **L과 P는 관문입니다.** 선행 연구가 이미 같은 질문에 답했거나, 파일럿에서 인터페이스를 바꿔도 성공률이 거의 움직이지 않으면 S에 들어가기 전에 연구 질문을 다시 다듬습니다.
- **L은 코드가 아니라 읽기입니다.** 그래서 v0 단계부터 같이 진행해도 됩니다.
- **실험 트랙은 v1, v2를 기다리지 않습니다.** 동기·비스트리밍 하네스만으로 충분합니다.

## 원칙

### 무인 실행

- 샌드박스가 없으면 무인 실행을 시작하지 않습니다. 샌드박스를 끄는 옵션은 대화형 실행에만 둡니다.
- API 키는 trace, 테스트 픽스처, 로그 어디에도 남기지 않습니다. 저장한 SSE 응답은 테스트 픽스처로 git에 들어가므로 특히 주의합니다.
- API 호출 비용 상한은 설정으로 걸 수 있게 합니다.
- 동시 실행 수에는 상한을 두지 않습니다. 직접 지켜봅니다.

### 기록

- 첫 실행부터 요청과 응답의 원본을 남깁니다. 기존 내용은 고치지 않고 덧붙이기만 하는 JSONL 파일로 저장합니다. 남기지 않은 원본은 돈을 다시 내야만 얻을 수 있기 때문입니다.
- 원본과 함께 다음 정보를 남깁니다.
  - 응답에 실제로 찍힌 모델 ID
  - 샘플링 설정
  - 하네스 커밋과 커밋되지 않은 변경(dirty)이 있었는지 여부
  - 스키마 버전
- 요청 원본이 남아 있으면 그때의 하네스 인터페이스를 trace에서 복원할 수 있습니다. 그래서 InterfaceSpec 분리는 P 직전으로 미룹니다.
- 다음 항목은 나중에 원본으로부터 만듭니다.
  - 대화 내용 없이 지표만 저장하는 모드
  - OTel GenAI 규약에 맞춘 필드 이름
  - 분석용 스키마

  OTel GenAI 규약은 아직 실험 단계입니다. 따르게 되면 어느 버전의 규약인지도 함께 기록합니다.

### 측정

- held-out 과제는 M에서 처음 엽니다. 인터페이스를 고치거나 루프를 돌리는 실행에는 넣지 않습니다.
- held-out 목록은 첫 파일럿 전에 확정해서 따로 떼어 둡니다. 구체적인 분리 방식은 열린 질문입니다.
- 파일럿에 쓴 과제는 held-out에 넣지 않습니다.
- 한 비교 안의 실행은 모두 같은 하네스 커밋(태그)과 같은 모델 스냅샷으로 돌립니다. 실험은 태그에서 돌리고, 하네스 개발은 main에서 계속합니다. 둘 중 하나라도 바뀌면 기준선부터 다시 측정합니다.
- 날짜로 고정된 스냅샷이 없는 모델(EXAONE 등)은 실행할 때마다 응답의 실제 모델 ID를 기록합니다. ID가 바뀌면 기준선부터 다시 측정합니다.

## 연구 주제

> 하네스 인터페이스는 특정 모델에 맞춰져 있다. 모델을 바꾸면 성공률이 얼마나 떨어지고, 자기개선 루프로 그 차이를 얼마나 메울 수 있는가?

- **실험 축:** GPT와 EXAONE입니다. 필요하면 HyperCLOVA X를 더합니다. 국내 모델에서 하네스가 어디서 깨지는지가 관심사입니다.
- **바꾸는 것:** 하네스 인터페이스만 바꿉니다. 루프 코드는 고정합니다.
- **2×2 교차 측정:** GPT용 인터페이스와 EXAONE용 인터페이스를 모두 같은 자기개선 루프로 만들고, 네 조합을 모두 held-out 과제로 측정합니다. 한쪽만 사람이 손으로 다듬으면 모델 차이와 방법 차이가 섞입니다. 결과 해석은 [GLOSSARY.md](../GLOSSARY.md)의 "2×2 교차 측정" 항목에 있습니다.
- **성능 하락의 두 성분:** 하락에는 모델 능력 차이와 인터페이스 부적합이 섞여 있습니다. "예상 성능"이라는 기준이 없으므로 처음부터 둘을 나눌 수는 없습니다. 루프를 돌린 뒤 회복된 만큼을 인터페이스 부적합분으로 사후에 측정합니다.
- **보고서 서술:** "성능이 떨어져서 루프를 만들었다"는 개발 동기로는 자연스럽습니다. 하지만 보고서에는 "루프를 두 모델에 똑같이 적용하고 교차 측정했다"로 써야 주장이 섭니다.
- **기반 단계:** Session과 컨텍스트 관리 실험(캐시, compaction)이 이 주제의 기반이 됩니다.

### 성공 기준

목표는 깊이 있는 발견 2~3개입니다. 발견 하나마다 다음이 붙어야 합니다.

- 반복 실행에서 나온 신뢰구간
- held-out 과제로 확인한 결과
- 실패를 원인별로 분류한 표
- 재현 스크립트
- 짧은 보고서 한 편

실패한 결과도 발견입니다. 예를 들어 "자동 개선으로는 차이를 X%밖에 못 메웠고, 원인은 Y였다"도 그대로 발견이 됩니다.

### 위험

- **통계적 검정력:** 과제 20개를 5번씩 돌려서는 아주 큰 차이만 구분됩니다. 과제 수를 늘리거나 효과가 큰 질문을 고릅니다. 차이가 드러나지 않으면 "차이 없음"이 아니라 "이 규모로는 판별 불가"라고 정직하게 씁니다.
- **비용:** 실험을 설계할 때 "과제 수 × 반복 수 × 평균 토큰"으로 예산을 먼저 계산합니다.
- **과적합:** 자기개선 루프가 평가 과제에 맞춰 인터페이스를 고치면 성공률이 부풀려집니다. 그래서 개발 과제와 held-out 과제를 분리합니다.

## 작업 방식

먼저 만들고, 나중에 기존 구현과 비교합니다. 내 설계를 먼저 확정한 뒤에 참고 구현을 읽으므로, 비교는 하되 영향은 받지 않습니다. "나는 X로 했는데 저쪽은 Y로 했다, 이유는 Z다"가 그대로 설계 기록이 됩니다. 여기에 세 가지를 보완합니다.

### 보완 1: 구현과 연구 주제는 순서가 다릅니다

| 대상 | 순서 | 이유 |
|---|---|---|
| 하네스 구현(루프, SSE, Session, 취소, MCP) | 먼저 만들고 나중에 읽습니다 | 남의 설계에 끌려가지 않고 내 설계를 먼저 세우기 위해서입니다 |
| 연구 주제(인터페이스 자동 개선) | 선행 연구를 먼저 읽습니다 | 누가 이미 했는지 모르면 새롭다고 주장할 수 없기 때문입니다 |

선행 연구 후보는 다음과 같습니다.

- 프롬프트 최적화: DSPy, GEPA 계열
- 실패에서 배우는 에이전트: Reflexion, ExpeL
- tool 문서와 설명을 자동으로 다듬는 연구

이 연구들을 훑어서 "기존 연구가 안 한 것"을 확정합니다. 모델 간 교차 적용(2×2)이나 국내 모델이 그 후보입니다. 남의 하네스 코드가 아니라 방법론을 읽는 것이므로, 먼저 만들고 나중에 읽는다는 원칙과 부딪히지 않습니다.

### 보완 2: 모듈마다 같은 사이클을 돕니다

1. **실제 데이터를 먼저 봅니다.** 예를 들어 파서를 짜기 전에 `curl`로 실제 SSE 스트림과 tool_call 델타를 받아 저장하고 직접 읽어 봅니다. 저장한 데이터는 그대로 테스트 픽스처가 됩니다.
2. **설계 메모를 씁니다.** 어떻게 만들지와 어디서 막힐 것 같은지를 예측까지 적습니다.
3. **직접 구현합니다.**
4. **예측과 실제를 비교합니다.** 예상하지 못한 문제가 가장 값진 기록입니다.
5. **참고 구현을 1~2개 읽고** 설계 메모에 비교 내용을 덧붙입니다.

모듈별로 읽을 참고 구현을 미리 정해 둡니다. 그래야 읽을거리가 끝없이 늘지 않습니다.

| 모듈 | 참고 구현 |
|---|---|
| SSE와 스트림 조립 | openai-python SDK |
| 에이전트 루프 | mini-swe-agent |
| 편집 형식 | Aider |
| MCP | 공식 Python SDK |
| 전체 구조 비교 | pi나 Codex 중 하나 |

### 보완 3: 막혔을 때는 단계를 밟습니다

1. **혼자:** 스펙 문서와 언어 문서만 보면서, 정해 둔 시간(예: 작업 세션 2번)까지 붙잡습니다.
2. **AI에게 묻기:** 개념이나 프로토콜에 관한 사실을 묻습니다. 예를 들어 "asyncio에서 CancelledError는 어떻게 전파되나?" 같은 질문입니다. 내가 쓴 코드에 대한 리뷰와 엣지 케이스 제안도 받습니다. 코드를 생성해 달라는 요청과 "기존 하네스는 어떻게 하나"는 묻지 않습니다.
3. **참고 구현:** 그래도 막히면 해당 부분만 읽습니다. 이 경우 "참고 후 구현"이라고 기록에 표시합니다.

## 미룬 결정

직접 만들면서 부딪혀 보고 정할 것들입니다. 각 결정을 다시 꺼낼 시점을 함께 적었습니다.

| 미룬 결정 | 다시 꺼낼 시점 |
|---|---|
| tool 세트, 편집 형식 | v0을 시작할 때 |
| bwrap 세부 설정, 메모리 제한 방식 | v0에서 무인 실행 장치를 구현할 때 |
| tool 선택 과제 세트 설계, E2E 과제의 형식·출처·개수 | E1, E0 |
| 실험에 쓸 모델, 실험별 예산, EXAONE 속도 제한 | E0 파일럿 직전 |
| 내부 메시지 모델 ADR | R0 이후 |
| InterfaceSpec 분리 | P 직전 |
| 지표 전용 모드, OTel 필드 이름, 분석 스키마 | 첫 분석을 할 때 |
| 대화형 권한 확인, REPL 범위, MCP·스킬·서브에이전트 | v2 이후. MCP 사양은 2026-07-28판에서 handshake와 session이 빠졌으므로 그때 다시 확인합니다 |
| 컨텍스트 관리, compaction | 긴 과제에서 컨텍스트가 넘칠 때 |
| LangGraph 비교 실험 | B 이후. 같은 과제 세트로 성공률, 토큰, 턴 수, 코드량, 감춰진 것과 통제할 수 없었던 것을 비교합니다 |
| 선행 연구 1차 지도(서브에이전트로 뽑을지) | L을 시작할 때 |
| Python 3.15 전환 | 의존성들이 3.15 지원을 표시할 때 |

## 열린 질문

- held-out 과제를 분리하는 구체적인 방식
- 모듈 사이클의 설계 메모(예측과 비교)와 "참고 후 구현" 표시를 어디에 둘지. ADR은 세 조건(바꾸기 비쌈, 맥락 없이 보면 의외, 실제 트레이드오프)을 모두 만족하는 결정에만 쓰기로 했으므로, 대부분의 모듈 메모는 ADR이 되지 않습니다.
