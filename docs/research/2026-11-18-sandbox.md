# bwrap 무인 실행 샌드박스 사전 조사 (WSL2, 2026-11-18)

> 2026-11-18 서브에이전트가 개발 기계(WSL2)에서 직접 실험하고 1차 출처로 확인한 보고서다. 처음에는 임시 폴더에 저장했으나 재부팅으로 사라져, 2026-11-19에 대화에 남아 있던 전문으로 다시 만들었다. 실험 스크립트(`alloc.py`, `killtest.py`, `deleg.sh`, `interop.sh`, `interop2.sh`, `tiocsti.py`)와 함께 받은 소스 사본은 복구하지 못했다. 사용자 이름과 로컬 경로는 지웠다.

결정은 하지 않고 사실, 선택지, 근거만 정리했다. "추론"이라고 표시하지 않은 내용은 이 기계에서 실험으로 확인했거나 1차 출처에 적혀 있는 것이다.

## 결론 요약

1. **bwrap 0.9.0은 setuid 없이 비특권 user namespace로 동작한다.** 요청한 옵션 `--unshare-net`, `--unshare-pid`, `--clearenv`, `--new-session`, `--die-with-parent`, `--as-pid-1`은 이 커널에서 모두 동작했다.
2. **메모리 제한 기반은 갖춰져 있다.** PID 1은 systemd이고, 사용자 systemd 인스턴스가 떠 있고, cgroup은 v2 단일 계층이며, 사용자 관리자에 memory·pids·cpu 컨트롤러가 위임되어 있다.
   - **`MemoryMax`만으로는 제한되지 않는다.** 이 기계에는 swap 5GB가 있어서 `systemd-run --user --scope -p MemoryMax=64M` 아래에서 200MB 할당이 swap으로 빠져나가 성공했다. `-p MemorySwapMax=0`을 같이 줘야 OOM kill이 났다.
   - **RLIMIT_AS와 RLIMIT_DATA는 프로세스별 한도다.** 두 값 모두 bwrap 안으로 상속되어 걸리지만, 256M 한도에서 200MB 프로세스 3개를 병렬로 띄우면 모두 성공했다. 또 node 24와 java 17은 AS=1G에서 기동하지 못했고, DATA=256M에서도 기동하지 못했다.
3. **시간 초과 때 트리 전체를 확실히 정리한 조합은 두 가지다.**
   - (a) `--unshare-pid --die-with-parent`로 띄우고 바깥 bwrap PID에 SIGKILL이나 SIGTERM을 보낸다.
   - (b) cgroup 단위로 kill한다. 방법은 `systemctl --user kill --signal=SIGKILL <scope>`나, 위임받은 하위 cgroup의 `cgroup.kill`이다.

   `os.killpg`는 `setsid`로 떼어 낸 자식을 놓친다. `--new-session`과 같이 쓰면 샌드박스 안 프로세스를 하나도 맞히지 못한다.
4. **`--die-with-parent`는 부모 프로세스가 아니라 부모 "스레드"의 종료에 묶여 있다.** 하네스가 수명이 짧은 워커 스레드에서 bwrap을 띄우면, 그 스레드가 끝날 때 샌드박스가 SIGKILL된다(실험으로 확인).
5. **호스트 보호에서 가장 큰 사실은 두 가지 탈출 경로다.** `--ro-bind / / --unshare-all --clearenv` 구성에서도 다음 두 경로가 막히지 않았다.
   - (i) WSL interop을 통해 `cmd.exe`가 샌드박스 밖 Windows 프로세스로 실행되었다.
   - (ii) `/run/user/1000/bus`로 systemd --user 관리자에 D-Bus 접근이 되었다.

   읽기 전용 바인드는 unix 소켓 connect를 막지 못하므로 둘 다 열려 있다. 홈 디렉터리(`~/.ssh`, `~/.config/gh`)와 Windows 사용자 프로필(`/mnt/c/Users/...`)도 읽힌다. `/usr`만 바인드하는 화이트리스트 레이아웃에서는 이 경로들이 보이지 않았다.
6. **TIOCSTI는 `--new-session` 없이도 막힌다.** 이 커널은 `CONFIG_LEGACY_TIOCSTI`가 꺼져 있고 `dev.tty.legacy_tiocsti=0`이어서 EIO가 반환됐다.

## B. 메모리 제한 선택지 비교

| 방식 | 이 기계에서 | 범위·정확도 | 대표 함정 |
|---|---|---|---|
| B-1. 명령마다 `systemd-run --user --scope -p MemoryMax=… -p MemorySwapMax=0` | 동작 | 프로세스 트리 전체 합계(cgroup). OOM kill로 집행 | swap, OOM 판별(종료 코드 불안정), failed unit 잔존, tmpfs 과금, D-Bus 의존, +11ms |

| B-3. `RLIMIT_AS` | 동작(상속됨) | 프로세스별 가상 주소 공간 | 가상 메모리를 크게 예약하는 런타임(node, java)이 기동 실패. 트리 합계는 못 막음 |

| B-5. 기타(`MemoryHigh`, `TasksMax`/`pids.max`, `--size`, `RLIMIT_RSS` 등) | 일부 확인 | — | 아래 참조 |

### B-1. systemd-run scope (cgroup v2)

- **이 기계에서 동작한다.** 사용자 관리자가 memory를 위임받았고, scope가 `app.slice` 아래에 만들어진다.
- **트리 전체에 적용된다.** 256M scope에서 200MB 프로세스 3개를 병렬로 띄운 결과는 OOMPolicy에 따라 달랐다.
  - 기본값(`OOMPolicy=stop`, 사용자 관리자 `DefaultOOMPolicy=stop`): 하나가 OOM kill된 뒤 systemd가 scope 전체를 종료했다(exit 143, "Terminated").
  - `-p OOMPolicy=continue`: 2개가 OOM kill되고 1개는 살아남았으며, 셸은 exit 0으로 끝났다.
- 커널 문서(memory.max): "If a cgroup's memory usage reaches this limit and can't be reduced, the OOM killer is invoked in the cgroup." 그리고 "Under certain circumstances, the usage may go over the limit temporarily." (https://docs.kernel.org/admin-guide/cgroup-v2.html)
- 함정:
  - **swap.** `memory.max`에는 swap이 포함되지 않는다. swap이 있는 이 기계에서는 MemoryMax=64M만으로 200MB 할당이 성공했다(VmSwap 148MB). 커널 문서(memory.swap.max): "If a cgroup's swap usage reaches this limit, anonymous memory of the cgroup will not be swapped out." systemd 문서(MemorySwapMax=): "Specify the absolute limit on swap usage of the executed processes in this unit." (https://www.freedesktop.org/software/systemd/man/255/systemd.resource-control.html)
  - **종료 코드로는 OOM을 판별할 수 없다.** 같은 OOM이라도 경우마다 종료 코드가 달랐다.
    - Python 단독: 137
    - scope + bwrap: 143. OOMPolicy=stop이라 systemd가 남은 bwrap을 SIGTERM으로 종료했기 때문이다.
    - 위임 하위 cgroup: 137

    systemd.scope 문서에 따르면 OOMPolicy는 다음과 같이 동작한다.
    - `stop`: "the event is logged but the unit is terminated cleanly by the service manager"
    - `kill`: `memory.oom.group=1`을 설정한다
    - `continue`: 로그만 남긴다
    - 기본값: `DefaultOOMPolicy=`를 따르고, `Delegate=`가 켜진 unit은 `continue`다

    (https://www.freedesktop.org/software/systemd/man/255/systemd.scope.html)

    OOM을 판별하려면 `memory.events`의 `oom_kill` 필드, unit의 Result(`oom-kill`), 사용자 journal 중 하나를 봐야 한다. 커널 문서: oom_kill은 "The number of processes belonging to this cgroup killed by any kind of OOM killer."
  - **failed scope가 남는다.** OOM으로 실패한 scope 4개가 `failed` 상태로 남아 있었다. `--collect`를 주면 남지 않았다. systemd-run 문서(--collect): "Unload the transient unit after it completed, even if it failed." (https://www.freedesktop.org/software/systemd/man/255/systemd-run.html) 추론: `--collect`를 쓰면 실패 뒤에 Result를 조회할 수 없다.
  - **tmpfs 사용량도 과금된다.** 샌드박스 안 `--tmpfs /tmp`(기본 크기 9.8G, RAM의 절반)에 150MB를 쓰자 64M scope에서 `dd`가 약 62MB 지점에서 OOM kill되었다. `--size 33554432 --tmpfs /tmp`를 주면 32MB에서 ENOSPC로 끝났다. 커널 문서의 근거는 두 곳이다. memory.stat의 file 항목: "Amount of memory used to cache filesystem data, including tmpfs and shared memory". Memory Ownership 절: "A memory area is charged to the cgroup which instantiated it…".
  - **D-Bus에 의존한다.** `XDG_RUNTIME_DIR`가 없으면 실패한다(실험). 추론: 사용자 systemd가 없는 환경(systemd=false인 WSL 배포판, 컨테이너, CI)에서는 쓸 수 없다.
  - **오버헤드.** 명령당 약 11ms가 더 든다(6ms → 17ms).
  - **같은 uid라면 샌드박스 밖에서는 한도를 바꿀 수 있다.** scope의 `memory.max`는 사용자 소유라 샌드박스 밖 같은 uid 프로세스는 수정할 수 있다. 샌드박스 안에서는 `/sys/fs/cgroup`이 ro 마운트라 수정할 수 없다(마운트 플래그로만 확인했고 쓰기는 시도하지 않음).
  - **PID 관계.** `--scope`에서는 systemd-run이 명령으로 exec되므로, Popen이 받은 PID가 곧 명령의 PID다(관찰). 문서 표현: "executed by systemd-run itself as parent process and will thus inherit the execution environment of the caller."

### B-2. 위임 cgroup 하위를 하네스가 직접 관리

- **실험 절차** (`deleg.sh`):
  1. `systemd-run --user --scope -p Delegate=yes`로 bash를 띄운다.
  2. bash가 자기 자신을 `supervisor/` 하위 cgroup으로 옮긴다(no-internal-process 규칙 때문).
  3. `cgroup.subtree_control`에 `+memory +pids`를 켠다.
  4. `job1/`을 만들고 `memory.max=64M`, `memory.swap.max=0`, `pids.max=64`를 쓴다.
  5. `sh -c 'echo $$ > job1/cgroup.procs; exec bwrap …'`로 실행한다.
- **결과:**
  - OOM kill, exit 137, `memory.events`: `oom 1 oom_kill 1`
  - `cgroup.kill` 한 번으로 setsid·nohup 자식을 포함한 5개 프로세스가 0개가 됨
  - `pids.max=64`에서 "Cannot fork", `pids.events: max 1`
  - `rmdir` 성공
- **사실로 확인한 차이:**
  - 명령마다 D-Bus를 왕복하지 않는다.
  - OOM을 `memory.events`로 판별할 수 있다.
  - 트리 정리가 `cgroup.kill` 한 번으로 끝난다.
- **비용:**
  - 하네스 자신이 위임된 unit 안에서 시작되어야 한다.
  - 하네스 프로세스를 leaf cgroup으로 옮겨야 한다.
  - 자식을 exec 전에 cgroup에 넣어야 한다. Python subprocess에는 이 기능이 없어서 실험에서는 셸 래퍼를 썼다. `preexec_fn`도 가능하지만 스레드 경고가 붙어 있다.
- **커널 문서:**
  - "No internal process" 제약: "only domain cgroups which don't contain any processes can have domain controllers enabled"
  - 위임받는 쪽이 쓸 수 있는 파일: 디렉터리 자체와 `cgroup.procs`, `cgroup.threads`, `cgroup.subtree_control`
  - `cgroup.kill`: "all processes located in the affected cgroup tree will be killed via SIGKILL."
  - `pids.max`: "Hard limit of number of processes."

  (https://docs.kernel.org/admin-guide/cgroup-v2.html)
- systemd 문서(Delegate=): "Units where this is enabled may create and manage their own private subhierarchy."

### B-3. RLIMIT_AS

- **이 기계에서 동작한다.** `prlimit`과 Python `preexec_fn` 둘 다로 건 제한이 bwrap 안 프로세스에 상속되었다. 256M에서 Python이 219MB 지점에 MemoryError를 냈다. 나머지 약 37MB는 인터프리터 자체의 가상 메모리다.
- **기준은 RSS가 아니라 가상 주소 공간이고, 프로세스별이다.** man getrlimit(2): "This is the maximum size of the process's virtual memory (address space)." 또 "A child process created via fork(2) inherits its parent's resource limits." 그리고 "Resource limits are preserved across execve(2)." (https://man7.org/linux/man-pages/man2/getrlimit.2.html)
- **함정(실험): 가상 메모리를 크게 예약하는 런타임이 깨진다.**
  - node v24.13.0: RSS 41MB인데 VmSize가 1.27GB다. AS=1G에서 기동 즉시 crash했다(exit 133 = SIGTRAP, V8 스택 출력).
  - java 17: AS=1G에서 "Failed to reserve memory for new overflow mark stack … Error occurred during initialization of VM"으로 실패했다.

  실패 형태가 MemoryError, ENOMEM, crash로 제각각이라 원인을 판별하기 어렵다.
- Python: `preexec_fn`은 "NOT SAFE to use in the presence of threads in your application. The child process could deadlock before exec is called." (https://docs.python.org/3.14/library/subprocess.html) 이 기계에는 대안으로 `prlimit` 실행 파일(util-linux 2.39.3)이 있다. `resource.prlimit(pid, …)`도 있다(Linux ≥ 2.6.36, glibc ≥ 2.13, 3.4+, https://docs.python.org/3.14/library/resource.html). 다만 spawn 뒤에 거는 방식이라 그 사이에 경쟁 구간이 생긴다(추론).

### B-4. RLIMIT_DATA

- **이 기계에서 동작한다.** 256M에서 Python이 250MB 지점에 MemoryError를 냈다.
- **커널 6.6에서 집계 대상:** `is_data_mapping(flags)`, 즉 `(flags & (VM_WRITE | VM_SHARED | VM_STACK)) == VM_WRITE`인 private·writable·non-stack 매핑이다(https://github.com/torvalds/linux/blob/v6.6/mm/internal.h). PROT_NONE으로 예약만 한 영역은 세지 않는다. 그래서 node와 java가 DATA=1G에서는 정상 기동했다.
- man getrlimit(2): "(since Linux 4.7) mmap(2), which fail with the error ENOMEM upon encountering the soft limit of this resource."
- 함정(실험):
  - DATA=256M에서는 node(exit 133)와 java(hs_err 생성) 둘 다 기동에 실패했다.
  - 프로세스별 한도다. DATA=256M에서 200MB 프로세스 3개를 병렬로 띄우면 모두 성공한다(합계 600MB).
- 추론: shared 매핑과 tmpfs에 `write()`로 쓰는 메모리는 집계되지 않는다.

### B-5. 기타

- **`MemoryHigh` / `memory.high`:** 넘으면 스로틀만 걸고 OOM은 일으키지 않는다. 커널 문서: "Going over the high limit never invokes the OOM killer and under extreme conditions the limit may be breached." systemd 문서는 이것을 "the main mechanism to control memory usage of a unit"로, MemoryMax를 "the last line of defense"로 설명한다. 실험하지 않았다.
- **`OOMPolicy=kill` → `memory.oom.group=1`:** 커널 문서: "killed together or not at all." 실험하지 않았다.
- **`TasksMax=` / `pids.max`:** 포크 폭탄을 막는다. `pids.max=64`로 실험해서 동작을 확인했다.
- **`--size N --tmpfs DEST`:** tmpfs 크기 상한이다. bwrap man: "It sets the size in bytes for the next tmpfs." 실험으로 확인했다.
- **`RLIMIT_RSS`:** 무효다. man: "This limit has effect only in Linux 2.4.x, x < 30".
- **`RLIMIT_NPROC`:** man: "a limit on the number of extant process (or, more precisely on Linux, threads)". 실험하지 않았다.
- **`RLIMIT_CPU`:** CPU 시간 기준이라 벽시계 기준 시간 초과를 대신할 수 없다(man 정의).
- **WSL VM 상한:** `.wslconfig`의 `memory=20GB`가 VM 전체 상한이다. 추론: 별도 제한이 없으면 샌드박스 명령 하나가 VM 메모리 전체를 쓸 수 있다.

## C. 시간 초과 시 프로세스 트리 정리

**실험 설계** (`killtest.py`, Python 3.14.10): bwrap 안의 `sh -c`가 아래 프로세스들을 띄운 뒤 foreground sleep에서 멈춘다.

- `sleep &` (일반 백그라운드)
- `nohup sleep &`
- `setsid sleep &`
- `setsid sh -c 'sleep &' &` (새 세션 + 이중 fork)
- `(trap '' TERM HUP INT; exec sleep) &` (SIGTERM 무시)
- foreground `sleep`

0.8초 뒤 kill 방식을 적용하고, 다시 0.8초 뒤 `pgrep -f '^sleep 9..'`로 살아남은 sleep 수(최대 6)를 센다. 각 변형이 끝날 때마다 `pkill`로 정리했고, 마지막 `pgrep` 결과는 0개였다.

| # | 구성 | 결과 |

### PDEATHSIG와 스레드

| 실험 | 결과 |
|---|---|
| 메인 스레드에서 spawn | 생존(정상) |
| 워커 스레드가 spawn한 뒤 0.3초 살아 있다가 종료 | bwrap이 SIGKILL(-9)됨 |
| `ThreadPoolExecutor` 워커에서 spawn | 워커가 살아 있는 동안은 생존, `shutdown()` 후 -9 |
| 워커 스레드가 spawn 직후 즉시 종료 | 생존 |

- prctl 문서: "The parent-death signal is sent upon subsequent termination of the parent thread"(https://man7.org/linux/man-pages/man2/PR_SET_PDEATHSIG.2const.html)
- bwrap 0.9.0은 샌드박스 자식을 clone한 뒤에야 `prctl(PR_SET_PDEATHSIG, SIGKILL)`을 호출하고, 호출 뒤 `getppid()`로 부모를 다시 확인하지 않는다(https://github.com/containers/bubblewrap/blob/v0.9.0/bubblewrap.c, `handle_die_with_parent` 376–382행, 호출 위치 2958행).
- 추론: 마지막 경우가 생존한 것은, 그 호출 전에 스레드가 끝나서 같은 프로세스의 다른 스레드로 reparent된 뒤에 신호가 설정되었기 때문으로 보인다.

### 확실히 동작한 조합 (사실)

1. **`--unshare-pid` + `--die-with-parent`로 띄우고 바깥 bwrap에 SIGKILL 또는 SIGTERM을 보낸다** (`Popen.kill()` / `terminate()`).
   - setsid, nohup, SIGTERM 무시까지 모두 정리됐다. 하네스가 SIGKILL로 죽어도 정리됐다(V14). `--new-session`, `--as-pid-1`, `--unshare-all`을 더해도 결과는 같았다.
   - 근거 1, pid_namespaces(7): init이 종료되면 "the kernel terminates all of the processes in the namespace via a SIGKILL signal"(https://man7.org/linux/man-pages/man7/pid_namespaces.7.html)
   - 근거 2, bwrap man(--die-with-parent): "Kills (SIGKILL) all bwrap sandbox processes in sequence from parent to child including COMMAND process when bwrap or bwrap's parent dies."
   - V5가 보여 주듯 `--die-with-parent`가 빠지면 이 조합은 성립하지 않는다.
2. **cgroup 단위 kill.** systemd scope에는 `systemctl --user kill --signal=SIGKILL`, 위임 하위 cgroup에는 `cgroup.kill`을 쓴다. pid ns 없이도 setsid 자식까지 정리됐다.
   - 다만 하네스가 죽어도 scope는 저절로 사라지지 않는다. systemd.scope 문서: scope 수명은 "the existence of at least one process in the scope"에 묶인다.
   - 추론: `--die-with-parent`와 같이 쓰면 하네스 크래시에도 정리될 것이다. 이 결합으로 크래시 실험은 하지 않았다.
3. **1과 2는 함께 쓸 수 있다.** scope + bwrap `--unshare-all --die-with-parent --new-session` 조합이 OOM 실험에서 정상 동작했다.

### 동작하지 않거나 조건부인 것 (사실)

- **`killpg`:**
  - `setsid`로 떼어 낸 자식은 빠져나간다.
  - SIGTERM을 쓰면 신호를 무시하는 자식이 남는다.
  - `--new-session`과 섞으면 샌드박스 프로세스를 하나도 맞히지 못한다.
- **`--as-pid-1`:**
  - 명령이 PID 1이 되므로 핸들러가 없으면 바깥에서 보낸 SIGTERM이 무시된다(V9). pid_namespaces(7): "Only signals for which the "init" process has established a signal handler can be sent". 예외는 SIGKILL과 SIGSTOP으로, "forcibly delivered when sent from an ancestor PID namespace."
  - 좀비를 수거하는 reaper도 없다. bwrap man: "Do not create a process with PID=1 in the sandbox to reap child processes."
- **유예 종료가 없다.** pid ns 방식에서 바깥 bwrap에 SIGTERM을 보내면 즉시 전원이 SIGKILL된다(V7). 추론: 유예 시간이 필요하면 `--json-status-fd`의 `child-pid`(호스트 PID)나 `systemctl --user kill --signal=SIGTERM`으로 먼저 신호를 보내야 한다. 실험하지 않았다.
- **`--unshare-pid`의 부수효과:** 명령이 정상 종료하면 남은 백그라운드 프로세스도 같이 죽는다(V10). 따라서 의도적으로 백그라운드 서버를 남기는 사용법은 불가능하다.

## D. 비밀값과 호스트 보호 관련 bwrap 옵션

**전제(README):** "bubblewrap is not a complete, ready-made sandbox with a specific security policy." 보안 모델은 bwrap 인자를 만드는 쪽이 "is responsible for defining its own security model". 또 "Everything mounted into the sandbox can potentially be used to escalate privileges." (https://github.com/containers/bubblewrap/blob/main/README.md)

| 옵션·대상 | 의미(출처) | 이 기계 실험 |
|---|---|---|
| `--clearenv` | "Unset all environment variables, except for PWD and any that are subsequently set by --setenv" (bwrap man, https://github.com/containers/bubblewrap/blob/main/bwrap.xml) | 붙이면 `FOO_SECRET`이 사라지고 `PWD`는 남음. 빼면 `FOO_SECRET=xyz`가 그대로 보임 |
| 다른 프로세스의 environ | `security/commoncap.c`의 `cap_ptrace_access_check`: 호출자와 대상의 user_ns가 다르면 대상 ns에서 `CAP_SYS_PTRACE`가 있어야 함(https://github.com/torvalds/linux/blob/v6.6/security/commoncap.c) | 같은 uid 호스트 프로세스의 `/proc/<pid>/environ`이 pid ns 없이도 "Permission denied". 단 `--proc /proc` 없이 `--ro-bind / /`만 쓰면 호스트 `/proc`이 그대로 보여 프로세스 869개가 나열됨. `--unshare-pid --proc /proc`이면 호스트 PID 자체가 보이지 않음 |
| 홈 디렉터리 | 위 README의 "Everything mounted…" | `--ro-bind / /`에서 `~/.bashrc`를 읽을 수 있고 `~/.ssh`, `~/.config/gh`가 보임(내용은 읽지 않음). ro라서 쓰기만 막히고 읽기는 열려 있음. `--tmpfs /home`이면 `/home`이 빔. 화이트리스트(`--ro-bind /usr /usr --symlink usr/bin /bin --symlink usr/lib /lib --symlink usr/lib64 /lib64 --proc /proc --dev /dev --tmpfs /tmp`)로 sh가 실행되고 `/mnt`, `/run`이 없음 |
| D-Bus·unix 소켓 | README: "if you bind a D-Bus socket into the sandbox, it can be used to execute commands via systemd." | `--unshare-all` + `--ro-bind / /` 안에서 `dbus-send`로 systemd --user Manager의 `SystemState`를 읽는 데 성공. `StartTransientUnit`은 호출하지 않음. `--tmpfs /run/user/1000`이면 소켓이 없음. `systemctl --user`는 `--unshare-pid`가 있을 때만 "No data available"로 실패했으나 `dbus-send`는 성공했으므로, pid ns는 차단 수단이 아님. `/run/user/1000`에 `gnupg/S.gpg-agent.ssh`, `pulse`, `snapd-session-agent.socket`, `pk-debconf-socket`이 있고, 사용자 관리자에서 Secret Service 구현(`pass-secret-service.service`)이 실행 중(존재만 확인) |
| `--unshare-net` | "network namespaces isolate the UNIX domain abstract socket namespace" (https://man7.org/linux/man-pages/man7/network_namespaces.7.html) | `lo`만 남고 외부 connect는 ENETUNREACH. 경로 기반 unix 소켓은 별개라서 위 D-Bus와 E절 WSL interop이 그대로 통함 |
| `--new-session`과 TIOCSTI | bwrap man: "This disconnects the sandbox from the controlling terminal which means the sandbox can't for instance inject input into the terminal", CVE-2017-5226 언급. README도 TIOCSTI를 seccomp로 걸러내지 않으면 `--new-session`이 필요하다고 함. 커널 `tiocsti()`: `if (!tty_legacy_tiocsti && !capable(CAP_SYS_ADMIN)) return -EIO;` (https://github.com/torvalds/linux/blob/v6.6/drivers/tty/tty_io.c). Kconfig LEGACY_TIOCSTI: "Its use is considered a dangerous legacy operation" (https://github.com/torvalds/linux/blob/v6.6/drivers/tty/Kconfig). `capable()`은 초기 user ns 기준: "Only a process with privileges in the initial user namespace can perform such operations." (https://man7.org/linux/man-pages/man7/user_namespaces.7.html) | `legacy_tiocsti=0`이라 `--new-session` 없이도 TIOCSTI가 EIO. `--new-session`이 없으면 `/dev/tty` 열기는 성공, 있으면 ENXIO. 부수효과: 바깥의 `killpg`가 샌드박스에 닿지 않음(V19). 추론: 단말 Ctrl-C도 샌드박스로 전달되지 않음 |
| `--disable-userns` | "Prevent the process in the sandbox from creating further user namespaces, so that it cannot rearrange the filesystem namespace…", "requires --unshare-user" | A절 참고. 옵션이 없으면 중첩 bwrap이 실행됨 |
| `--unshare-pid` + `--proc /proc` | 새 pid ns와 그에 맞는 procfs | 위 environ 행 참고 |
| `/sys/fs/cgroup` | — | `--ro-bind / /` 안에서 ro. 샌드박스가 자기 cgroup 한도를 바꾸지 못함(쓰기는 시도하지 않음) |
| no_new_privs | README: "bubblewrap uses `PR_SET_NO_NEW_PRIVS` to turn off setuid binaries." | 안에서 `NoNewPrivs: 1`, `CapEff: 0` |
| seccomp | `--seccomp FD`, `--add-seccomp-fd FD` 옵션이 있음 | 조사하지 않음 |

## E. WSL2 특유의 주의점

1. **Windows interop이 샌드박스 탈출 경로가 된다(실험).** 결과는 다음과 같다.

   | bwrap 구성 | 결과 |
   |---|---|
   | `--ro-bind / / --unshare-all --die-with-parent --new-session --clearenv` | `cmd.exe /c echo` 성공 |
   | 위 + `--setenv WSL_INTEROP …` | 성공 |
   | pid ns 없이 `--unshare-net`만 | 성공 |
   | `/usr`만 + `/mnt/c` | `execvp … No such file or directory` (binfmt 인터프리터 `/init`이 없음) |
   | `/usr` + `/mnt/c` + `/init` | 실패(`UtilGetPpid … Failed to parse: /proc/1/stat`) |
   | `/usr` + `/mnt/c` + `/init` + `/run/WSL` | 성공 |
   | `--ro-bind / /` + `--tmpfs /run/WSL` | 실패 |
   | `--ro-bind / /` + `--tmpfs /mnt` | `cmd.exe` 파일이 없어 실패 |

   - Microsoft 문서: Windows 도구는 "Have the same permission rights as the WSL process. Run as the active Windows user." (https://learn.microsoft.com/en-us/windows/wsl/filesystems)
   - 추론: 실행된 Windows 프로세스는 Linux namespace와 cgroup 바깥에 있으므로 `--unshare-net`, 메모리 제한, kill 방식이 적용되지 않을 것이다. 실험하지 않았다.
   - `WSLInterop`은 F 플래그 없이 등록되어 있다. binfmt_misc 문서에 따르면 F가 없으면 경로가 실행하는 쪽의 마운트 ns에서 해석된다("the path is resolved in the mount namespace and root of whoever runs the binary", https://docs.kernel.org/admin-guide/binfmt-misc.html). 그래서 `/init`을 숨기면 interop이 실패한다.
   - 끄는 방법(Microsoft 문서):
     - `wsl.conf`의 `[interop] enabled=false`: 배포판 전체에 적용되고 재시작이 필요하다(https://learn.microsoft.com/en-us/windows/wsl/wsl-config).
     - root로 `echo 0 > /proc/sys/fs/binfmt_misc/WSLInterop`: "Disabling interop will not persist between WSL sessions" (filesystems 문서).
2. **Windows 파일시스템이 보인다.** `/mnt/c`는 9p drvfs이고 rw, uid=1000이다. `--ro-bind / /` 안에서는 ro로 보이지만 읽기는 된다. Windows 사용자 프로필 아래 파일을 읽을 수 있음을 확인했다. 자동 마운트는 `wsl.conf [automount] enabled` 기본값 true 때문이다.
3. **WSLg 소켓이 보인다.** `/mnt/wslg/.X11-unix/X0`과 `/mnt/wslg/PulseServer`가 `--ro-bind / /` 안에서 보였다. `--tmpfs /tmp`를 쓰면 `/tmp/.X11-unix`는 가려지지만 `/mnt/wslg` 경로는 남는다. X11이나 Pulse 접근으로 생기는 위험은 조사하지 않았다.
4. **swap.** `.wslconfig`의 swap 기본값은 "25% of memory size on Windows rounded up to the nearest GB"이고, 이 기계는 5GB다. 그래서 cgroup 방식에는 `MemorySwapMax=0`(또는 `memory.swap.max=0`)이 필요했다. `memory` 기본값은 "50% of total memory on Windows"이고, 이 기계는 20GB로 지정되어 있다(wsl-config 문서).
5. **systemd.**
   - `wsl.conf`의 `[boot] systemd` 기본값은 false다. 다만 `wsl --install`로 설치한 최신 Ubuntu는 기본으로 systemd를 쓴다(https://learn.microsoft.com/en-us/windows/wsl/systemd). 이 기계는 true다.
   - 문서: "systemd services will NOT keep your WSL instance alive." 이 기계는 Linger=yes다.
   - 추론: 다른 WSL 배포판이나 설정에서는 `systemd-run --user`를 쓸 수 없을 수 있다.
6. **cgroup.** `wsl.conf [automount] cgroups` 기본값은 `v2`이고, `.wslconfig [wsl2] isolateDistroCgroup` 기본값은 true다("Requires cgroup v2"). 이 기계는 v2 단일 계층이다.
7. **커널과 LSM.** WSL은 Microsoft 커널이라 AppArmor가 비활성이고, Ubuntu 24.04 네이티브의 비특권 userns 제한 sysctl이 아예 없다. 추론: 네이티브 Ubuntu 24.04로 옮기면 bwrap이 AppArmor 정책의 영향을 받을 수 있다. 확인하지 않았다.
8. **네트워크.** NAT 모드다. `--unshare-net`을 쓰면 상관없다. 네트워크를 공유할 때 Windows 호스트에 접근할 수 있는지는 조사하지 않았다.

## F. 확인하지 못한 것과 불확실한 것

- **D-Bus 탈출 자체는 실행하지 않았다.** `StartTransientUnit`을 호출하지 않았고, README 문구와 Manager 접근 성공을 근거로 한 추론이다. Secret Service와 gpg-agent 소켓을 실제로 쓸 수 있는지도 미확인이며, 존재만 확인했다.
- **WSL interop의 미확인 부분:**
  - `/mnt`를 숨기고 `/init`과 `/run/WSL`만 보이는 상태에서, 쓰기 가능한 경로에 둔 PE 파일을 실행할 수 있는지.
  - Windows 쪽 프로세스가 pid ns 종료나 cgroup kill로 정리되는지. 정리되지 않을 가능성이 있다(추론).
- **binfmt_misc 범위.** 6.6에서 binfmt_misc가 namespace별인지 전역인지 문서로 확인하지 않았다. 샌드박스 안에서도 동작했다는 관찰만 있다.
- **`set -m`(V18)은 결론이 없다.** dash가 tty 없이 job control을 켜지 않아 생존 0이 나왔다. 다만 "프로세스 그룹을 벗어날 수 있다"는 성질은 setsid로 확인했다.
- **RLIMIT_AS의 다른 대형 예약 사례는 실험하지 않았다.** Go, ASan, 멀티스레드 glibc arena, JVM 옵션별 차이 등. node와 java만 확인했다.
- **실험하지 않은 메모리·프로세스 설정:** RLIMIT_NPROC와 user namespace의 상호작용, MemoryHigh, OOMPolicy=kill(`memory.oom.group`).
- **`--die-with-parent`의 경쟁 구간.** 그 구간에서 하네스 "프로세스 전체"가 죽으면 PDEATHSIG가 하네스에 묶이지 않을 수 있다. 소스를 근거로 한 추론이고 실험하지 않았다. scope와 결합한 상태에서 하네스가 크래시하는 실험도 하지 않았다.
- **asyncio 경로는 실험하지 않았다.** `asyncio.create_subprocess_exec`로 띄우는 경우다. 추론: 이벤트 루프 스레드에서 띄우면 스레드 함정에 걸리지 않는다.
- **seccomp와 Landlock은 조사하지 않았다.** `CONFIG_SECURITY_LANDLOCK=y`이지만 securityfs가 마운트되어 있지 않아 활성 LSM 목록을 확인하지 못했다.
- **샌드박스 안에서 cgroup 파일과 `/mnt/c`에 실제로 쓰는 시도는 하지 않았다.** 마운트 플래그 `ro`로만 판단했다.
- **`/proc/<pid>/cmdline` 노출은 확인하지 않았다.** 호스트 `/proc`이 그대로 보이는 경우다.
- **출처 버전 차이.** upstream README와 bwrap.xml은 main 브랜치 기준이다. README에는 setuid 모드가 제거되었다고 적혀 있다. 설치된 0.9.0과 다를 수 있어, 옵션 설명은 로컬 man(`/usr/share/man/man1/bwrap.1.gz`)과도 대조했다.
- **systemd-run 문서와 관찰의 차이.** 문서의 "executed by systemd-run itself as parent process" 표현과 달리, 실제로는 같은 PID로 exec되었다. 관찰을 우선했다.

## 실험 정리 상태

- 실험 프로세스 0개(`pgrep`로 확인), bwrap 0개, probe scope 0개.
- OOM으로 failed 상태가 남은 transient scope 4개는 `systemctl --user reset-failed`로 정리했다.
- 저장소에는 쓰지 않았다.
